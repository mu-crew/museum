# Design notes

## Goal

The main goal is keeping every pi session safely backed up in one place. Search is secondary and rare, and an agent does it using a skill.

## Decisions

- **Store = plain folders under rsync.** Pi session files are append-only JSONL files with UUID names, so `rsync --append-verify` without `--delete` makes a correct, incremental, never-deleting copy.
- **Per-host folders instead of merging.** Each machine owns `<store>/<hostname>/`, so writes can never race. A project worked on from several machines appears under several host folders, and a glob such as `*/*project*` covers them all.
- **No index.** Around 1.3 GB and 1,800 sessions, `rg` over the store takes about a second, and the agent can rank and summarize results itself.
- **`museum-search` over hand-written recipes.** Recipes in the skill had to be quoted twice to run over ssh, and broke on the store host's login shell. ssh starts `python3 -` on the store host and the script arrives on stdin, so the remote login shell only parses a few quoted words and the store host needs no museum install. `rg` picks the matching files when the store host has it (about 0.8s over the store, against 2.8s for a pure-Python scan), and Python parses only those. It ranks by where the term appears: a user or assistant turn's text first, then anything else (tool output, thinking, tool-call arguments), and it drops sessions where only the recorded system prompt mentions it. Every session in a project records the same AGENTS.md and docs, so a word in them otherwise matches every session in the project. Within a tier, project folders come before mu workspace folders, because an orchestrator session holds the decisions its workers carry out, and then the session with the most candidate turns comes first. Date order put a newer passing mention above the session that debated the topic: for "herdr", the 46-turn session that designed mu's multiplexer layer ranked 9th of 24. `--newest` keeps date order for "what is the latest on X". Three `rg` passes do the work: mention counts, system-prompt mention counts (a session where the two are equal is dropped, with no file read), and lines that may be a turn saying the term. Python parses candidate lines only until one per session confirms, because the regex cannot tell a turn's text from its thinking or tool calls. That takes 0.3 to 2.5s on the 1.3 GB store, against about 6s to classify every mention in Python. The searching session (`$PI_SESSION_ID`, passed as `--skip`) is left out.
- **TOML config, with the store split.** The first config was `KEY=value` lines, once sourced as shell, with the store as one rsync-style `host:/path` string that the scripts split on the first colon. `config.toml` names the parts: `machine`, then `[store]` with `host`, `path` and `ssh_mux_only`. The scripts read it with `tomllib` and reject unknown keys, a relative path, a `host` with a colon in it and `ssh_mux_only` without a `host`, so a typo fails in the footer instead of quietly syncing to the wrong place. `host` alone marks an ssh store, rather than a `[store.ssh]` / `[store.local]` pair: the one mistake that shape guards against, a forgotten `host` line, is caught instead by requiring a local store's folder to exist. The sync creates only `<path>/<machine>/`, and `install.sh` creates the store folder once, so a stray `path` meant for the store host fails rather than filling a local copy and reporting success. The config file carries these rules as comments; `install.sh` and the legacy converter each write it, and a test fails if their output differs. `tomllib` needs Python 3.11, which drops macOS's Command Line Tools Python 3.9; macOS clients already need Homebrew for rsync 3. An older `python3` gets that message in the footer, not an ImportError. The store host's side of a search is handed the folder with `--store`, so it reads no config and runs on any `python3`. Both scripts carry the same config code, since each must stay a single file, and a test fails if the two copies differ.
- **Python for the scripts, not sh.** Both scripts started as POSIX sh. The search half was jq programs inside sh strings, and the sync needed `flock` on Linux and `lockf` on macOS. Stdlib Python has JSON, argparse and one `fcntl.flock` for both platforms, and it brings tests (`unittest`), linting (ruff) and type checks (ty). The scripts stay single files with no dependencies, so installing still means running `install.sh` and nothing else.
- **Repo metadata in the session, not beside it.** The extension writes a `museum` custom entry (`pi.appendEntry`) at session start: git common dir (the same for every worktree of a repo), remote, branch, commit, `MU_WORKSTREAM`, `MU_AGENT_NAME`. It travels inside the session file, so the sync needs no second file, and pi keeps it out of the model's context. Pi writes a session file only once it has a conversation, so an empty session leaves nothing behind. Sessions from before this change have no entry, and `museum-search` falls back to the folder name.
- **No daemon, no server-side binary.** The store host needs only ssh and rsync.
- **pi triggers the sync.** Sessions only change while pi runs. A pi extension syncs at `session_start` (catch-up, if due), `agent_settled` (if due, 10 minutes) and `session_shutdown` (now). It runs in the pane's environment, so ssh agents and forwarded keys work. An idle agent is still a pi process, so overnight work syncs too. Failures show in pi's footer (see the next decision). Lost: the tail of a crashed session on a host that is reclaimed before pi runs there again.
- **The sync decides the footer label; every pi only shows it.** The label used to be computed by each pi from `state` at its own `session_start` and `agent_settled`. With many agents on a node, an idle one kept showing "ok" through an outage another agent's sync had hit, and kept showing "failing" after another agent's sync recovered. Now `museum-sync` writes the label (empty while backups work) as the `warning` field of `state.json`, next to `status`, `time` and `message`, atomically, and each pi re-reads it every 5 seconds and only calls `setStatus` when it changes. The rule lives in one place, under test. pi decides only what no sync can write: `no backup yet` (no `state.json`) and `cannot run museum-sync` (spawn failed, or exit 126/127). A crash inside the script is caught and recorded like a failed sync. The old `no backup for 3d` label is gone: it needs a clock, and a pi running means syncs are being triggered, so a sync that keeps not succeeding already shows as failing. State moved from `~/.cache/museum` to `$XDG_STATE_HOME/museum` (`~/.local/state/museum`), because a cache may be wiped and this is state, and `state` (`key=value` lines) became `state.json`, which the extension parses without a regex. The old folder is not migrated: it holds no sessions, only sync bookkeeping, and the first sync starts afresh.
- **Concurrency lives in `museum-sync`, not the extension.** A node can run 10+ agents. The script takes a non-blocking kernel lock and exits if another sync holds it; the due check happens under the lock. A flush (`--now`) first writes a `pending` mark, and the holder loops until no mark is left, re-checking after it unlocks. The lock is `flock(2)` on an fd, released on death; the fd is not inheritable, so ssh, rsync and any orphan they leave cannot keep it; rsync and ssh timeouts bound a hung connection.
- **No automatic retry over a fresh ssh connection.** `BatchMode=yes` blocks password and passphrase prompts, but not a security-key agent asking for a touch. A retry could cost the user a touch, so a failed sync waits for the next due one. Sessions stay on local disk, and `--append-verify` resumes, so waiting loses nothing. One ssh connection per sync: the remote `mkdir` rides rsync's connection through `--rsync-path`.
- **`ssh_mux_only` for store hosts that need a human to log in.** The sync runs only over an existing ControlMaster, checked with `ssh -O check`, which never connects. With no master, it records `no ssh master for <host>` and skips, so the footer asks the user to open one. All ssh auth methods are also disabled, so a master that dies between the check and rsync fails instead of prompting. Here a retry costs nothing, so a failure retries once after `MUSEUM_RETRY_DELAY` (30s) while the master is up. Opting in is explicit because the script cannot tell ahead of time whether a fresh connection would prompt.

## Rejected or deferred

- **A central SQLite FTS index.** SQLite locking does not work across rsync copies or network filesystems. It would need `ssh host sessidx …`, which means a binary installed on the host.
- **Per-host index shards plus a merged cache on each client.** This works, but it adds complexity that occasional grep searches don't need.
- **Hashed file names or content-addressed chunks.** They aren't needed, because per-host folders already rule out collisions and readable paths make it easy to narrow a search.
- **Compressing session files (`.jsonl.zst`).** Search can handle it: `rg -z` reads plain and `.zst` files in one pass, and on the store `find` took about 1.2s instead of 0.4s. The cost is in the sync. rsync appends only to plain files, so a session the store has compressed gets uploaded whole on every sync. Stopping that means sending only recently changed files (`--files-from`), and then the sync no longer repairs the store by itself. The store host would also need `zstd`. Put the store on a compressing filesystem instead: on btrfs with `compress-force=zstd:3`, the 865M store takes 272M on disk. Compressing each file with zstd would bring it to 229M.
- **Existing tools.** chronicle (git transport; rewrites session files) doesn't fit. adobe/pi-session-search (scans local files) is the fork candidate if `museum-search` proves too limited.

## Possible later additions

- **A failure log.** `state.json` holds only the last result, so a failure that a later sync fixes leaves no trace.

- **An FTS index built on the store host,** if grep gets slow. The raw files remain the source of truth, so an index can be built at any time.
