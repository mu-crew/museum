# Design notes

## Goal

The main goal is keeping every pi session safely backed up in one place. Search is secondary and rare, and an agent does it using a skill.

## Decisions

- **Store = plain folders under rsync.** Pi session files are append-only JSONL files with UUID names, so `rsync --append-verify` without `--delete` makes a correct, incremental, never-deleting copy.
- **Per-host folders instead of merging.** Each machine owns `<store>/<hostname>/`, so writes can never race. A project worked on from several machines appears under several host folders, and a glob such as `*/*project*` covers them all.
- **No index.** Around 1.3 GB and 1,800 sessions, `rg` over the store takes about a second, and the agent can rank and summarize results itself.
- **`museum-search` over hand-written recipes.** Recipes in the skill had to be quoted twice to run over ssh, and broke on the store host's login shell. ssh starts `python3 -` on the store host and the script arrives on stdin, so the remote login shell only parses a few quoted words and the store host needs no museum install. `rg` picks the matching files when the store host has it (about 0.8s over the store, against 2.8s for a pure-Python scan), and Python parses only those. It ranks by where the term appears: a user or assistant turn's text first, then anything else (tool output, thinking, tool-call arguments), and it drops sessions where only the recorded system prompt mentions it. Every session in a project records the same AGENTS.md and docs, so a word in them otherwise matches every session in the project. Within a tier, project folders come before mu workspace folders, because an orchestrator session holds the decisions its workers carry out, and then the session with the most candidate turns comes first. Date order put a newer passing mention above the session that debated the topic: for "herdr", the 46-turn session that designed mu's multiplexer layer ranked 9th of 24. `--newest` keeps date order for "what is the latest on X". Three `rg` passes do the work: mention counts, system-prompt mention counts (a session where the two are equal is dropped, with no file read), and lines that may be a turn saying the term. Python parses candidate lines only until one per session confirms, because the regex cannot tell a turn's text from its thinking or tool calls. That takes 0.3 to 2.5s on the 1.3 GB store, against about 6s to classify every mention in Python. The searching session (`$PI_SESSION_ID`, passed as `--skip`) is left out.
- **Python for `bin/`, not sh.** Both scripts started as POSIX sh. The search half was jq programs inside sh strings, and the sync needed `flock` on Linux and `lockf` on macOS. Stdlib Python has JSON, argparse and one `fcntl.flock` for both platforms, and it brings tests (`unittest`), linting (ruff) and type checks (ty). The scripts stay single files with no dependencies and target 3.9, the macOS system Python, so installing still means running `install.sh` and nothing else.
- **Repo metadata in the session, not beside it.** The extension writes a `museum` custom entry (`pi.appendEntry`) at session start: git common dir (the same for every worktree of a repo), remote, branch, commit, `MU_WORKSTREAM`, `MU_AGENT_NAME`. It travels inside the session file, so the sync needs no second file, and pi keeps it out of the model's context. Pi writes a session file only once it has a conversation, so an empty session leaves nothing behind. Sessions from before this change have no entry, and `museum-search` falls back to the folder name.
- **No daemon, no server-side binary.** The store host needs only ssh and rsync.
- **pi triggers the sync.** Sessions only change while pi runs. A pi extension syncs at `session_start` (catch-up, if due), `agent_settled` (if due, 10 minutes) and `session_shutdown` (now). It runs in the pane's environment, so ssh agents and forwarded keys work. An idle agent is still a pi process, so overnight work syncs too. Failures show in pi's footer. Lost: the tail of a crashed session on a host that is reclaimed before pi runs there again.
- **Concurrency lives in `museum-sync`, not the extension.** A node can run 10+ agents. The script takes a non-blocking kernel lock and exits if another sync holds it; the due check happens under the lock. A flush (`--now`) first writes a `pending` mark, and the holder loops until no mark is left, re-checking after it unlocks. The lock is `flock(2)` on an fd, released on death; the fd is not inheritable, so ssh, rsync and any orphan they leave cannot keep it; rsync and ssh timeouts bound a hung connection.
- **No automatic retry over a fresh ssh connection.** `BatchMode=yes` blocks password and passphrase prompts, but not a security-key agent asking for a touch. A retry could cost the user a touch, so a failed sync waits for the next due one. Sessions stay on local disk, and `--append-verify` resumes, so waiting loses nothing. One ssh connection per sync: the remote `mkdir` rides rsync's connection through `--rsync-path`.
- **`SSH_MUX_ONLY=1` for store hosts that need a human to log in.** The sync runs only over an existing ControlMaster, checked with `ssh -O check`, which never connects. With no master, it records `no ssh master for <host>` and skips, so the footer asks the user to open one. All ssh auth methods are also disabled, so a master that dies between the check and rsync fails instead of prompting. Here a retry costs nothing, so a failure retries once after `MUSEUM_RETRY_DELAY` (30s) while the master is up. Opting in is explicit because the script cannot tell ahead of time whether a fresh connection would prompt.

## Rejected or deferred

- **A central SQLite FTS index.** SQLite locking does not work across rsync copies or network filesystems. It would need `ssh host sessidx …`, which means a binary installed on the host.
- **Per-host index shards plus a merged cache on each client.** This works, but it adds complexity that occasional grep searches don't need.
- **Hashed file names or content-addressed chunks.** They aren't needed, because per-host folders already rule out collisions and readable paths make it easy to narrow a search.
- **Existing tools.** chronicle (git transport; rewrites session files) doesn't fit. adobe/pi-session-search (scans local files) is the fork candidate if `museum-search` proves too limited.

## Possible later additions

- **A failure log.** `state` holds only the last result, so a failure that a later sync fixes leaves no trace.

- **An FTS index built on the store host,** if grep gets slow. The raw files remain the source of truth, so an index can be built at any time.
